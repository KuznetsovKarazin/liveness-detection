Asked by the coordinator on the C2 card on 19 November 2026, in the evening, after merging PR #29 (merge `362c653` into
`research/pad-2026`): the coordinator verified commit `a7b160f` and approved the NUAA pre-registration; after the merge

missing in one of the two BN states. At the end of the runs, the two ACER gaps, their contrast with the subject

**Status of this delivery.** This folder holds the command of the two NUAA runs (`livenesslab/scripts/pad_arch_run.py`),
its configuration (`livenesslab/delivery/archrun/pad_arch_run.json`), its synthetic test suite and mutation check, and
their logs. **No run has been executed**: no `check-estimator`, no training, no checkpoint, no result. On the real

Nothing was run on Linux by the author.

The command applies the rule that the pre-registration announced (`PROTOCOL.md` §7 and §11 of
`research/pad-arch-comparison/`): every training and evaluation of the NUAA plan on the machine of the official trial,
with the same threads and versions, "a declared rule that the runner of the 48 trainings will have to apply".

## The command

`pad_arch_run.py` has three subcommands:

- `check-inputs`: read-only, TensorFlow not imported, nothing written. It checks the configuration (a closed set), the
  pinned files (the configuration of the pre-registration, the code, the record of the official trial, `run_order.csv`
  and `run_caps.csv`, byte for byte equal to the files regenerated by the functions of the pre-registration, the
  configurations of PRs #27 and #28), the thread environment variables and the machine and version rule (the same
  functions, at the same point, as `check-estimator` and `run`), the inputs of the pre-registration and, for each of
  the 24 reference cards (12 of arm B per accepted run), the fitting and dev keys against the manifests. It does not
  check the git work tree.
- `check-estimator`: the check that `PROTOCOL.md` §3 requires: the re-estimation "must first reproduce the statistics
  of run 20261114-BNRECAL-a10a082 within the tolerance of PRs #27 and #28, otherwise the work stops" (below).
- `run`: one run (`--run nuaa_patience_4` or `--run nuaa_patience_12`), 24 trainings in one process; it needs
  `--i-am-authorized` and `--estimator-check` with the folder of a PASS of `check-estimator`.

The official sequence, from the root of the author's working repository, with no `TF_NUM_INTRAOP_THREADS` or
`TF_NUM_INTEROP_THREADS` in the environment (the lines of the docstring of the command and of the field `operations`
of the configuration):

```bash
.venv/bin/python -I -B scripts/pad_arch_run.py check-inputs
nohup caffeinate -dims .venv/bin/python -I -B scripts/pad_arch_run.py check-estimator --i-am-authorized > <a log file outside the repository> 2>&1 &
# commit (results/ is versioned)
nohup caffeinate -dims .venv/bin/python -I -B scripts/pad_arch_run.py run --run nuaa_patience_4 --estimator-check results/archrun/<YYYYMMDD>-ARCHEST-<commit> --i-am-authorized > <a log file outside the repository> 2>&1 &
# commit
nohup caffeinate -dims .venv/bin/python -I -B scripts/pad_arch_run.py run --run nuaa_patience_12 --estimator-check results/archrun/<YYYYMMDD>-ARCHEST-<commit> --i-am-authorized > <a log file outside the repository> 2>&1 &
# commit
```

`check-estimator` and `run` refuse a git work tree that is not clean, so a commit separates the commands. Why each part
of the launch line (`operations`): `nohup` because a SIGHUP (closing the terminal) would stop the command as FAIL (SIGTERM does too); the output redirected to a
file outside the repository because otherwise `nohup` writes `nohup.out` in the current folder, the work tree is no
longer clean and the command refuses; `caffeinate` because the cap counts elapsed real time, time asleep included.
SIGUSR1 to the pid written in `status.json` stops a command as INCOMPLETE at the next check. One heavy process at a
time on the machine. The run folders are `results/archrun/<YYYYMMDD>-ARCHEST-<commit>` and
`results/archrun/<YYYYMMDD>-ARCHRUN-p4|p12-<commit>`, with the suffix `-r<k>` for an attempt k > 1.

## Machine and thread check (requested by the coordinator)

The reference is the record of the official trial `20261119-ARCHTRIAL-b8f7cca`: its `status.json` and `trial.json`,
pinned by SHA-256 in the configuration and equal to the lines `trial/status.json` and `trial/trial.json` of the
`SHA256SUMS` of the pre-registration package (itself pinned by SHA-256). The trial must have status PASS.

- **Machine and versions** (`machine_rule`). Fields compared: `processor`, `core_levels`, `ram_gb`, `os`,
  `logical_cpus`, `architecture` (read from the system now) and `python`, `numpy`, `tensorflow_installed` (read
  without importing TensorFlow), `keras`, `platform`. In the trial record: Apple M5 Pro; cores as named by the system,
  5 Super and 10 Performance; 24.0 GB RAM; macOS 27.2.1; 15 logical CPUs; arm64; Python 3.11.16, NumPy 1.26.4,
  TensorFlow 2.15.0, Keras 2.15.0, platform `darwin`. A field is equal only if present and not null on both sides and
  identical. On a difference the command stops with `RESULT: FAIL (<subcommand>)`, naming the fields; no folder and no `status.json`
  are written, nothing is trained.
- **Thread environment variables** (`thread_environment_rule`). `TF_NUM_INTRAOP_THREADS` and `TF_NUM_INTEROP_THREADS`
  are read; a variable that contradicts the 10 and 10 threads of the pre-registration is refused, and the variables
  found must be the same as in the trial record, where both were absent. So a variable present, even at 10, stops the
  command: this is stricter than `training.threads.rule` of the pre-registration, which admits the variables present
  and equal to the values (a choice of the author, below).
- **When.** Both rules are applied identically in `check-inputs`, `check-estimator` and `run`: right after the pinned
  files are checked (variables first, then machine and versions), before any data input is loaded and before any folder
  is created.
- **Threads set by the runner** (`threads_rule`). In `check-estimator` and `run`, right after TensorFlow is imported
  (after the inputs are loaded, before any TensorFlow operation), the runner sets 10 intra-op and 10 inter-op threads
  through `tf.config.threading` and reads them back (`pad_arch_comparison.set_threads`, the function of the trial).
  Effective threads other than 10 and 10, or TensorFlow initialised before the threads could be set: FAIL before any
  training (`run`) or any re-estimation (`check-estimator`), with the reason in `status.json`; effective threads other
  than 10 stop in `set_threads` with the values read back in the reason; when they are 10 and 10, the thread record
  (requested, effective, the two environment variables found, set by the runner) is compared with the trial's
  (requested 10 and 10, effective 10 and 10, both variables absent, set by the runner) and the comparison
  (`threads_rule`) is recorded: given the earlier checks it cannot differ (in the mutation check, its failure path in
  `check-estimator` and the order of its recording in `run` are declared redundant).
  During a run the effective threads are read back before each training and after the dev scoring of
  each model in phase 1; a change gives FAIL.
- **Where it is recorded.** `status.json` of every check-estimator and run folder (`machine_rule` and `threads`;
  `threads_rule` once the threads have been set and read back as 10 and 10); `estimator_check.json`; `summary.json` of a run (`machine`, `environment`, `machine_rule`,
  `threads`, `threads_rule`, and the threads read back before and after each model); `report.md` states the machine
  and threads. A run accepts a `check-estimator` record only if both rules were met there.
- **Tests** (`livenesslab/scripts/check_pad_arch_run.py`, synthetic), one per check:
  - `TestCMachineRule`: `test_same_machine_passes_and_is_recorded`, `test_different_machine_stops`,
    `test_null_or_missing_on_both_sides_stops`, `test_different_versions_stop`, `test_threads`,
    `test_threads_missing_or_null_on_both_sides`;
  - `TestGCheckInputs`: `test_thread_environment_at_10_refused` (`check-inputs` refuses the variables present at 10);
  - `TestHRunFlow` (the flow of `run`): `test_processor_different_from_the_trial_stops_before_any_folder`,
    `test_other_machine_fields_stop_before_any_folder`,
    `test_intra_op_environment_variable_contradicting_refused_before_any_folder`,
    `test_inter_op_environment_variable_contradicting_refused_before_any_folder`,
    `test_environment_variables_at_10_refused_before_any_folder`, `test_thread_record_different_from_the_trial`,
    `test_requested_intra_op_threads_not_10_refused_before_any_folder`,
    `test_requested_inter_op_threads_not_10_refused_before_any_folder`,
    `test_effective_intra_op_threads_not_10_stop_before_training`,
    `test_effective_inter_op_threads_not_10_stop_before_training`,
    `test_tensorflow_initialised_before_the_threads_stops_before_training`, `test_threads_changed_during_a_training`,
    `test_order_of_the_plan_and_threads_before_training`, `test_final_status_metadata`;
  - `TestLEstimatorFlow` (the flow of `check-estimator`): `test_threads_set_and_gpu_hidden`,
    `test_machine_different_refused_before_any_folder`, `test_environment_variables_at_10_refused_before_any_folder`.

## What a run does

Before the run folder is created: the checks of `check-inputs` on the pinned files, the thread environment variables,
the machine rule, the `check-estimator` record (PASS, same configuration and code, official for an official run,
machine and thread rules met, every model passed), a clean work tree, the attempt rule. Then: the inputs, the 12
reference cards of arm B of the accepted run at the same patience with their keys, TensorFlow and the threads (above),
the GPU hidden.

- **Phase 1**, for each of the 24 positions of `run_order.csv` in order (folds 1–4, seeds 42, 43, 44, LivenessNet then
  ResNet-18): the fitting and dev frames of the unit assembled (an explicit check refuses any other role) and their
  keys checked against the reference card; the training with the trainer of the technical trial
  (`pad_arch_comparison.trial_trainer`), the patience of the run, at most 12 epochs; a non-finite value in the new
  history, of either network, ends the run as FAIL right after that training, before the checkpoint, with the field
  and the epoch as the reason (a choice of the author, below); the `.keras` checkpoint saved right after; the checks of
  the training card of the accepted runs; for LivenessNet, the history check against the card of the same fold and
  seed in the accepted run at the same patience (`20261106-SESSABLRUN-d999458` for patience 4,
  `20261109-SESSABLRUN-6a50265` for patience 12): five fields, difference 0, the first differing epoch reported; for a
  finite difference the run continues and the model stays in the comparison (`PROTOCOL.md` §7); the dev scored with
  the saved checkpoint by the scorer of the accepted runs, with the `val_loss` recomputed from the logits against the
  minimum of the card.
- **Phase 2**, after the 24 trainings, in the same order: the checkpoint reloaded (SHA-256 checked) and checked
  against the architecture register of the pre-registration; the dev in the ordinary BN state with the evaluator of
  PR #27, whose scores are then compared with the phase-1 scores (agreement, below); the BN statistics re-estimated on
  the fitting set of the unit, on an in-memory copy, with the estimator of PR #27 and its checks; the dev in the
  re-estimated state with the same evaluator; per BN state the EER threshold of the project on the dev, the decisions
  at 0.5 and at that threshold, and the one-class count of definition (a).
- **At the end**: the dev frame identifiers compared between the two networks of each unit, between the units of a
  fold and between the two BN states (`pad_arch_definitions.prepare_units` and `same_frames`); no role other than
  fitting and dev assembled; the configuration, the code, the pinned files, the reference cards and the
  `check-estimator` record unchanged since the start.
- **Cap**: the hours of wall time of `run_caps.csv` for the run (5.00 each), checked before every training, at the end
  of every epoch and before every inference pass.

Outputs: `status.json` and `run.log`; `public/` with `models.csv`, `one_class.csv`, `summary.json`, `report.md`,
`SHA256SUMS` (aggregates with no frame or subject identifier, only counts and the SHA-256 of the sorted identifiers;
scanned before writing); `restricted/` with, per model, the checkpoint, the card, the phase-1 dev scores, the dev
scores in the two BN states with the frame identifiers, the re-estimated BN statistics, and `SHA256SUMS`. The
restricted outputs are what the evaluation command will need. `status.json` records `started`, `finished`, the elapsed
time, the process CPU time, the commit and the SHA-256 of the configuration, the code and the inputs. The commit
recorded by a run is a commit of the author's working repository, which also holds unpublished work in progress; the
link between a run and the published code is the SHA-256 of the configuration, of the command and of the pinned code
files recorded in `status.json`, to be compared with the files of this folder.

## Outcomes

| outcome (exit code) | when | what is kept | what it means for the comparison |
|---|---|---|---|
| PASS (0) | all 24 models complete in both phases, every check passed | all outputs | the 24 models of the run go to the evaluation command |
| INCOMPLETE (2) | the cap, or SIGUSR1 | the model in progress in phase 1 is removed ("discarded at the cap"); the public outputs of the complete models | no further step starts; a stop in phase 1 leaves every model without its BN states evaluated; the run is not resumed (below) |
| MISMATCH (4) | on the ordinary dev, the phase-1 scorer and the evaluator differ by more than 1e-5 on a frame, or disagree on a decision at 0.5 or at the EER threshold, for at least one model | the trainings are not interrupted; the restricted files with their `SHA256SUMS`; the discrepancy per model in `status.json` | no public output of results |
| FAIL (1) | any other failed check (machine, threads, inputs, a non-finite value in a new history, frame identifiers, PR #27 checks, an error, SIGHUP or SIGTERM) | `status.json` with the reason, `run.log`, the restricted files of the complete models (the files of the model in progress are removed); public outputs removed | no public output |

A MISMATCH prevails over INCOMPLETE (the status also records the stop). A new attempt after INCOMPLETE, FAIL or
MISMATCH is started only after the outcome has been reported to the coordinator on the C2 card (`after_stop`). The
coordinator asked for a check that stops the primary analysis if one of the 12 fold and seed combinations is missing in
one of the two BN states; it will be in the evaluation code.

## The estimator check (`check-estimator`)

`PROTOCOL.md` §3: the re-estimation "must first reproduce the statistics of run 20261114-BNRECAL-a10a082 within the
tolerance of PRs #27 and #28, otherwise the work stops". `check-estimator` re-estimates, on an in-memory copy of each of the 36 accepted LivenessNet checkpoints at
patience 4 (fitting and dev only), the BN statistics with the estimator of this command; it applies the checks of PR
#27 and compares the installed statistics and the dev probabilities after the re-estimation with the BNRECAL run, with
the tolerances of the configuration of PR #28 (statistics: relative 1e-4 and absolute 1e-6; dev probabilities: 1e-5,
no discordant decision at 0.5). Outcomes: PASS (0); MISMATCH (4, at least one model outside, documented per model in
`estimator_check.csv`: the runs are refused); FAIL (1); INCOMPLETE (2, cap of 240 minutes of wall time or SIGUSR1).

## What the commands read

From the configuration field `test` (the command requires its exact text, `TEST_READ` of the script): **no test frame
is assembled or evaluated, no test score or metric is read.**

- `check-inputs` and `run`: the configuration, the configuration of the pre-registration, the pinned code; the record
  of the official trial and the package `SHA256SUMS`; `run_order.csv` and `run_caps.csv`; the configurations of PRs #27
  and #28; what the pre-registration's `load_inputs` reads: the five M2 manifests (to index the cache; `official_test`
  and `cnn_test` are NUAA's official lists, not the test role of the folds), the cache, hashed whole with its label and
  subject members read, the extracted frames file, loaded whole with the SHA-256 of every frame (both frame files also
  hold frames of the held-out subjects), files of the cells run, of the folds run and of the two accepted runs; the 12
  training cards of arm B of each accepted run; with `--estimator-check`, the record of `check-estimator`.
- `run`, in addition: the image arrays of the cache, loaded whole; of all the frames it assembles only the fitting and
  dev frames of arm B; it reads back its own checkpoints.
- `check-estimator`: the same pinned files (with the configurations of the two accepted runs, read through the
  pre-registration's `load_config`), what the loader of PR #27 reads (the same manifests and frame files, files of the
  cells and folds runs; of the parent run at patience 4, its public `aggregate.json` only as bytes for the SHA-256,
  never parsed, since it holds test metrics, and per model card, dev scores, threshold and checkpoint) and, of run
  `20261114-BNRECAL-a10a082`, its status, checksums, public results and run record, and per model the score and
  statistics files, which hold dev and fitting rows only; it assembles only fitting and dev frames.
- No command loads the fold schema (`fold<k>_test.csv`) or opens a `<model>_test_scores.csv`.

## Choices of the author

Not fixed by the pre-registration; each stated as a choice of the author in the configuration
(`choices_of_the_author`, with the field that gives the detail):

1. **Two phases** (`sequence.reason`): between two trainings the run keeps the TensorFlow operations of the accepted
   runs except the assembly and scoring of the test; the BN re-estimation and the scoring of the two BN states come
   after the 24 trainings, so that they add no TensorFlow operation between two trainings. Consequence: a stop in phase
   1 leaves every model without its BN states evaluated.
2. **Checkpoint** (`checkpoint.when`): saved by this runner right after the trainer of the trial returns, with the
   lines of the accepted trainer (`.keras`, written to a temporary name and renamed); the technical trial saved no
   checkpoint (`PROTOCOL.md` §7).
3. **Order of the re-estimation in ResNet-18** (`estimator.order_rule`): the order of its specification, checked on the
   graph of the model; the pre-registration does not fix the order in a network with branches; layers that do not feed
   each other may come in any order (test `test_order_between_independent_layers_does_not_change_the_result`).
4. **`check-estimator` as a command of its own** (`estimator_check.where`), before the two runs, so that no TensorFlow
   operation precedes the first training in the process of a run, as in the accepted runs.
5. **The estimator check on all 36 models** of the BNRECAL run (arms B, A* and B′), not only the 12 of arm B, and on
   both criteria of PR #28 (statistics and dev probabilities), as PR #28 did.
6. **The cap of `check-estimator`** (`estimator_check.cap_rule`): 240 minutes of wall time, the cap of the configuration
   of PR #27, which covered the same re-estimation of the same 36 models plus a baseline; the pre-registration fixes no
   cap for this check.
7. **No automatic resume** (`after_stop`): a run that stops keeps its folder and its outcome and is never continued; a
   new attempt is started only after the outcome has been reported to the coordinator on the C2 card, and repeats the 24 positions from position 1 in a new
   process and folder, reusing nothing, so that every training keeps its position in its process.
8. **Attempts** (`attempts`): `--attempt` must be the last attempt of the same run + 1, every earlier attempt recorded
   with its status; the official output root is `results/archrun`; another root, outside the repository only, with
   `--unofficial-out-root`, recorded as not official; the command recorded with every argument.
9. **Versions compared** (`machine_rule.consequence`): Python, NumPy and the platform in addition to the TensorFlow and
   Keras versions that the pre-registration names; tensorflow-metal and OpenCV not compared (the GPU is hidden; OpenCV
   is not used); every field required present and not null.
10. **Machine model, not physical unit** (`machine_rule.scope`): another unit of the same model with the same fields
    and versions passes; the pre-registration does not say whether "the machine of the official trial" means the model
    or the unit.
11. **The whole thread record of the trial compared**, environment variables included (`machine_rule.consequence`):
    they must be the same as in the official trial, where both were absent, checked before any folder in
    `check-inputs`, `check-estimator` and `run`; stricter than `training.threads.rule` of the pre-registration, which
    admits them present and equal to the values, so that the runs repeat the conditions of the official trial exactly.
12. **One evaluator for both BN states** (`dev_evaluation.evaluator`): thresholds, decisions, one-class counts and every
    comparison use the scores of the evaluator of PR #27 in both states; the phase-1 scorer is kept for the `val_loss`
    check, as in the accepted runs, and its scores are kept.
13. **Binding agreement between the two scorers** (`dev_evaluation.agreement`): the rule of PRs #27 and #28 (1e-5, no
    discordant decision at 0.5), extended by the author to the EER threshold of the ordinary state, with outcome
    MISMATCH.
14. **History outcome "different" also when only the number of epochs differs** (`history_check.first_differing_epoch`).
15. **First differing epoch of a model** across the five fields, an epoch present in one history only counting as
    differing (`history_check.first_differing_epoch`).
16. **A non-finite value** (`history_check.non_finite`): in the new history of a training, of either network, it ends
    the run as FAIL right after that training, before the checkpoint is saved, with the field and the epoch as the
    reason (the training card, which holds the history, cannot hold a non-finite value, as in the technical trial);
    `PROTOCOL.md` §7 ("the model stays in the comparison") covers finite differences, which a card can hold. A
    non-finite value in a reference card (the 24 reference cards of the accepted runs hold none) is reported as a
    difference of its field at its epoch, and the run continues.
17. **A dev without one class** gives no EER threshold (NA) and a not-evaluable one-class result instead of a failure;
    the NUAA dev of every fold holds both classes.
18. **Names of the outputs**: the public and restricted files and their columns, the run id
    `YYYYMMDD-ARCHRUN-p4|p12-<commit>[-r<k>]` and the folder `results/archrun`.
