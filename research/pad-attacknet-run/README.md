Second step of card C5, as `PROTOCOL.md` §11 of the PR A package (pull request #34, folder
`research/pad-attacknet-comparison/`): the pull request with the command and configuration of the six runs of the 72
AttackNet trainings, published and linked on the C5 card before the runs start. **No run and no check-estimator has
been executed**; `check-machine` and `check-inputs` were run on the real inputs (read only, logs below).

## What is fixed

The configuration pins by SHA-256, and every command checks before any folder is created:

- the PR A configuration `delivery/anetcmp/pad_anet_comparison.json` (SHA-256 `6f5297d0…`), read and validated with
  `pad_anet_comparison.load_config`, with everything it pins (the C2 pre-registration, the PR #27 configuration, the C2
  trial record, the public files of the C2 evaluation, the architecture file);
- the code: the PR A and C2 modules (`pad_anet_comparison.py`, `pad_anet_definitions.py`, `pad_anet_models.py`,
  `pad_arch_*.py`, `nuaa_*.py`, `m2_writers.py`, `path_guard.py`, `package_rules.py`); `pad_anet_run.py` itself is
  recorded with its SHA-256 in every output;
- the record of the official trial `20261122-ANETTRIAL-a951ed0` (`trial/status.json`, `trial/trial.json` of the PR A
  package) and the PR A `SHA256SUMS` that lists them; the trial is accepted only by `pad_anet_comparison.load_trial`,
  that is only if it was produced by the PR A configuration and code, and only if it was official (every test hook
  unset);
- `plan/run_matrix.csv`, `plan/run_order.csv` and `plan/run_caps.csv` of the PR A package, also listed in its
  `SHA256SUMS`, which must be equal byte for byte to the files regenerated from the PR A configuration, the public files
  of the C2 evaluation and the trial (`pad_anet_comparison.plan_texts`): the positions of each run are read from
  `run_matrix.csv`, its cap from `run_caps.csv` (`cap_wall_hours`), never rewritten;
- the PR #27 configuration (the same file as in the PR A configuration) and the PR #28 configuration, for
  `check-estimator` (PROTOCOL.md §3).

The six runs, in the order of `run_order.csv`, each in one process, 12 positions each (folds 1–4 × seeds 42, 43, 44):

| run | network | patience | cap (hours of wall time) | estimated hours (`plan/run_caps.csv`) |
|---|---|---|---|---|
| `anet_v1_p4` | AttackNetV1 | 4 | 2.50 | 0.60–1.22 |
| `anet_v2_1_p4` | AttackNetV2_1 | 4 | 2.50 | 0.61–1.24 |
| `anet_v2_2_p4` | AttackNetV2_2 | 4 | 2.00 | 0.50–1.03 |
| `anet_v1_p12` | AttackNetV1 | 12 | 2.50 | 1.22 |
| `anet_v2_1_p12` | AttackNetV2_1 | 12 | 2.50 | 1.24 |
| `anet_v2_2_p12` | AttackNetV2_2 | 12 | 2.00 | 1.03 |

Recipe and trainer: those of the technical trial (`pad_anet_comparison.anet_trainer`, the declared copy of the C2
trainer with rule (n); the model built with the registry, `create_model` and its defaults), with the early stopping
patience of the run; CPU only, GPU hidden, 10 intra-op and 10 inter-op threads set and read back; the machine model, the
versions and the thread record equal to those of the C5 trial (`pad_arch_run.machine_rule`, `thread_environment_rule`,
`threads_rule` applied to the C5 trial).

Each run (the sequence of the C2 runs, `pad_arch_run`):

- phase 1, for each position: fitting and dev frames of the unit (arm B; their keys checked against the cards of the
  accepted runs), training, rule (n) on the history and on the restored weights (`pad_anet_definitions.training_outcome`),
  the dev and the fitting scored with the model in memory in the ordinary state, the checkpoint saved, the card, the dev scored with the scorer of the accepted
  runs and the val_loss checked against the card;
- phase 2, for each evaluable model: the checkpoint reloaded and checked against the registry, the ordinary dev, the BN
  statistics re-estimated on the fitting set of the unit (`pad_arch_run.reestimate`, the order of the registry), the
  consistency pass, the re-estimated dev, the checks of PR #27, the agreement of the phase-1 scorer with the evaluator,
  thresholds, decisions and counts of both BN states.

Rule (n) (PROTOCOL.md §6 (k)/(n)): a non-finite value in the history does not stop the run (quantity and first epoch
recorded; restored epoch = that of the smallest finite val_loss); a model without a finite val_loss, with non-finite
restored weights, with non-finite scores or logits on the dev or on the fitting in either BN state (ordinary: the
in-memory passes of phase 1; re-estimated: phase 2, the consistency pass for the fitting), or with non-finite
re-estimated statistics is **not evaluable**: recorded with the reason in `models.csv`, `summary.json`, `report.md` and
`status.json`, no phase 2, and the run goes on with the other models. A model found not evaluable in phase 1 has no
checkpoint and its card in `restricted/` says so (`rule_n.evaluable` false, `not_evaluable_reason`); a model found not evaluable in phase 2 keeps its checkpoint and phase-1 dev scores in `restricted/`, marked
not evaluable in `models.csv`, and the evaluation does not score it on the test. The in-memory passes are inference
only, after the training and after its epoch times are recorded: no state of the model, no seed and no recorded time
changes, and the checkpoint is the same as without them. Outcomes: PASS 0,
FAIL 1, INCOMPLETE 2 (cap or SIGUSR1), MISMATCH 4 (scorer and evaluator disagree; no public result), as in C2.

No test frame is assembled or evaluated, no test score or metric is read (`TEST_READ` of `pad_anet_run.py`, also the
field `test` of the configuration).

## Commands, in order, from the root of the repository

Order of the official commands: this pull request published and its link on the C5 card; then `check-estimator` (not
before the link); then the six runs in the order of the table, with a commit after each command (`results/` is
versioned and the commands refuse a tree that is not clean). Each command is launched from a zsh with `setopt
nobgnice`, through the launch script, which runs `check-machine` and `check-inputs` first:

```
setopt nobgnice
ANETRUN_LOG_DIR=<a folder outside the repository> ANETRUN_ATTEMPT=1 nohup zsh delivery/anetrun/launch.zsh check-estimator > <a log file outside the repository> 2>&1 &
```

then a commit, and for each run of the table, in its order, with a commit after each one:

```
setopt nobgnice
ANETRUN_LOG_DIR=<a folder outside the repository> ANETRUN_ATTEMPT=1 ANETRUN_ESTIMATOR=results/anetrun/<run id of check-estimator> nohup zsh delivery/anetrun/launch.zsh run anet_v1_p4 > <a log file outside the repository> 2>&1 &
```

The script launches `caffeinate -dims .venv/bin/python -I -B scripts/pad_anet_run.py check-estimator --attempt 1
--i-am-authorized` and `… run --run anet_v1_p4 --estimator-check results/anetrun/<id> --attempt 1 --i-am-authorized`;
the same commands can be given by hand.

SIGUSR1 to the pid in `status.json` stops a command as INCOMPLETE at its next check. Rule of use: SIGUSR1 is sent only
for a cause outside the results (for example the machine must be released), never after looking at the histories or
the dev outcomes of the run, and the cause is stated in the report.

Expected last lines: `check-machine: machine and versions equal to the C5 trial 20261122-ANETTRIAL-a951ed0 (11
fields); thread environment variables TF_NUM_INTRAOP_THREADS absent, TF_NUM_INTEROP_THREADS absent, as in the trial;
TensorFlow not imported; nothing written` and `RESULT: PASS (check-machine)`; `RESULT: PASS (check-inputs)`; `RESULT: PASS (check-estimator)` (the 36
models of `20261114-BNRECAL-a10a082` reproduced; in C2 it took 1,544.5 s of wall time, cap 240 minutes);
`RESULT: PASS (run anet_v1_p4)`. Before each command: power mode 0, power adapter and lid open, `setopt nobgnice`, no
`TF_NUM_` variable, no other heavy process, `git status --porcelain` empty (the conditions of the trial, `PROTOCOL.md`
§7 of PR A). A run stopped at its cap, by SIGUSR1, by a FAIL, a MISMATCH or an interruption is not resumed:
after its outcome is reported on the C5 card it is repeated as a new attempt from position 1 (`--attempt N+1`),
retraining every position, those not evaluable included; a run is never repeated because of a not evaluable model; the
evaluation reads only the last attempt of each run, which must be PASS with phase 1 complete for the 12 positions
(amended `PROTOCOL.md` §6 (k)/(n)). `--date` is accepted only with `--unofficial-out-root`: an official run id carries
the date of the launch.

**Launch with the conditions recorded.** `delivery/anetrun/launch.zsh` (from the root of the repository; parameters in
environment variables, no path in the script): it stops before any command if its nice value is not 0 (a background
job of a zsh without `setopt nobgnice` runs at nice 5), writing the value in the conditions file; it refuses a log folder
inside the repository; it runs `check-machine` and `check-inputs` (with `--estimator-check` for a run) and does not
launch the command if either fails; then it runs the command under `caffeinate -dims` and propagates its exit code. It
writes in the log folder `<check-estimator or run name>-attempt<N>-conditions.txt`, whose first line is the heading
written by the script ("Conditions of …, written by delivery/anetrun/launch.zsh (not by the runner)."), and which
attests: date, `uptime` (load) and CPU usage at the start and at the end; `sw_vers`; the power mode and low power mode
(`pmset -g`) and the power source (`pmset -g batt`); the nice value of the script; the number of `TF_NUM_` variables
set; the commit and the number of lines of `git status --porcelain`; the full outputs and exit codes of
`check-machine` and `check-inputs`; the command and its exit code. It does not attest the lid or the absence of other
processes beyond what load and CPU usage show. The script does not publish the file: after each official command the
author copies it unchanged, as `conditions.txt`, into the folder of the records of that run, which is published with
the report of the runs (as `trial/conditions.txt` in PR A). The suite runs the script with a fake runner in a temporary
folder (macOS only).

Outputs in `results/anetrun/<run id>/` (run id `YYYYMMDD-ANETRUN-<v1|v2_1|v2_2>-p<4|12>-<commit>[-r<k>]`,
`YYYYMMDD-ANETEST-<commit>[-r<k>]` for check-estimator): `status.json`, `run.log`; `public/` `models.csv`,
`one_class.csv`, `summary.json`, `report.md`, `SHA256SUMS` (counts and SHA-256 only, no subject or frame identifier);
`restricted/` per model `.keras`, `_card.json`, `_dev_scorer.csv`, `_dev_ordinary.csv`, `_dev_re-estimated.csv`,
`_bn_statistics.json` and `SHA256SUMS`, not published.

## Choices of the author

The closed list of the field `choices_of_the_author` of the configuration: the two phases and their order, as in C2;
the dev and the fitting scored with the model in memory before the checkpoint is saved (for rule (n)); the checkpoint saved by this
runner after the trainer returns, as in C2; the card check of C2 with the non-finite history values read as +inf (the
restored epoch expected is that of the smallest finite val_loss); check-estimator as a command of its own; no

record compared with the C5 trial; the binding agreement of scorer and evaluator (MISMATCH); the dev frames checked per
fold across the models of a run and the two BN states; the names and columns of the outputs; the deviation of PR A
recorded in amended copies.

## The two amendments of the PR A protocol

`pr34_amended/PROTOCOL.md` is the PR A `PROTOCOL.md` with two paragraphs added, both marked "Amendment of 22 November
2026" and both fixed before any of the six runs; `pr34_amended/README.md` is the PR A `README.md` with the first sentence
of "What follows" corrected; both copies also carry a heading that says so, and nothing else differs. The originals
stay unchanged in the PR A folder; a test of the suite rebuilds the amended
copies from them and checks that they differ only there (the SHA-256 of the originals are in the PR A `SHA256SUMS`
pinned by the configuration).

- §6 (k)/(n), after its list: a run stopped at its cap, by SIGUSR1, by a FAIL, a MISMATCH or an interruption is repeated,
  after its outcome is reported on the C5 card, as a new attempt from position 1, retraining every position (those not
  evaluable included; a run is never repeated because of a not evaluable model), and the evaluation reads only the last
  attempt of each run, PASS with phase 1 complete for the 12 positions; this replaces the pre-registered "resumed only
  for the missing trainings" (it is the rule of C2, a run resumed halfway would mix models of two processes, no number
  changes if no run stops); with the clarification on the checkpoint of a model found not evaluable in phase 2.
- §7, after "What follows each outcome": pull request #34 was opened on 22 November 2026 at 09:23:36 (+0100), before the
  comment with the outcome of the trial (09:34:29), contrary to the pre-registered order; as announced in the body of
  pull request #34, the deviation is recorded in `PROTOCOL.md` §7; it concerns the order of publication only.

## What follows

As `PROTOCOL.md` §11 of PR A: the link to this pull request on the C5 card; then check-estimator and the six runs, in
the order of the plan; then one comment on the C5 card after the six runs: the estimator check and, for each run, its
run id, outcome, trainings complete out of 12, models not evaluable and anomalies, with the totals per patience out of
36 and the logs. If an official command does not end in PASS (FAIL, INCOMPLETE, MISMATCH, an interruption, or
check-estimator not PASS), its outcome is reported on the C5 card at once, before any new attempt (amended
`PROTOCOL.md` §6 (k)/(n)). Then the evaluation code and configuration published, with the link on the card, before the
NUAA test is read.
